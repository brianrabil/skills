# B2 style

Write code as if it flies in the B-2. A failure is expensive, nothing is allowed to be vague, and the code must be easy to inspect by someone who did not write it. This is not ceremony: every rule below exists to make wrong states impossible or loud, and right behaviour obvious.

The posture: you are the engineer responsible for this subsystem on an aerospace programme. Before writing, state the stage's contract to yourself: inputs, outputs, limits, and what happens when each input is wrong.

## Shape: pipelines of thick stages

Organise work as a pipeline of named stages, each a substantial block with one job:

```
parse → validate → plan → execute → verify → report
```

- **One direction.** Data flows forward through stages. A stage never reaches back into an earlier one or into global state.
- **Thick stages, thin seams.** A stage is a real unit of work (often 20–70 lines), not a one-line wrapper. Seams between stages are plain typed values, not callbacks, events, or shared mutable objects.
- **Typed boundaries.** Each stage takes and returns an explicit type (`ParsedRequest` → `ValidRequest` → `Plan` → `Result`). Parsing produces the type; nothing downstream casts (`as`) or re-checks shape.
- **Effects at the edges.** Pure stages in the middle; I/O (disk, network, process, clock) only in the stages that name it (`execute`, `report`).
- **The pipeline reads like the spec.** The top-level function is the list of stages in order, so a reviewer sees the whole flow in one screen.

## The rules

1. **Assert invariants.** Check preconditions, postconditions, and assumptions with assertions at stage boundaries and inside loops where state changes. Aim for at least two assertions per non-trivial function. In TypeScript use a small `assert(condition, message)` that throws; in Zig `std.debug.assert`; in Rust `assert!`/`debug_assert!`. Assertions are not error handling: they guard programmer mistakes, so a failure stops the program loudly.
2. **Bound everything.** Every loop, retry, queue, buffer, recursion depth, payload, and wait has an explicit, named limit (`max_retries = 3`, `queue_capacity = 256`, `timeout_ms = 5_000`). Nothing grows without a ceiling. When a limit is hit, that is a handled outcome, not a crash.
3. **Errors are values.** Expected failures (bad input, missing file, network down) are typed results handled where they happen or returned deliberately. No silent `catch {}`, no `|| fallback` recovery that hides a failure, no `any`, no swallowing. Unexpected states are assertion failures.
4. **Names carry units and meaning.** `timeout_ms`, `size_bytes`, `max_units`, `retry_count`, `started_at`. Booleans read as facts (`is_paused`, `has_lock`). No abbreviations a newcomer would have to guess.
5. **Control flow you can see.** Early returns over nested conditionals. No deep nesting (three levels is the ceiling). No clever one-liners that hide branches. No recursion where a bounded loop works.
6. **Mostly glue, at a high level.** Most code joins our own libraries (vgpu, Stealth, the units SDK, Brain, eve, the AI SDK) with maintained dependencies, at the highest level of abstraction they offer. Prefer Bun built-ins over npm packages. Hand-roll only where it pays off, such as native Zig clients. Never write our own abstraction layers, plugin systems, or class hierarchies "for later".
7. **Determinism where it matters.** Seeded randomness, injectable clocks, replayable inputs. Anything stateful and important gets a simulation or property test, the way Zig World's simulator replays storage faults.
8. **State in plain sight.** Data you can print and read: JSON, JSONL, SQLite rows. One owner per piece of state. No hidden caches without a bound and an eviction rule.
9. **Comments explain why.** The code says what. Comments record the reason, the limit's origin, or the failure it prevents. Delete comments that restate the code.
10. **Verify before done.** A stage is finished when its assertions hold under its tests, its limits are exercised, and its failure paths have been run at least once, not when the happy path works.

## The signature

Code written in this style should be recognisable at a glance, the way a reader can tell a file came from a particular codebase without reading its header. The recognition comes from structure repeated everywhere, never from banners, watermarks, or "generated by" comments.

Every module follows the same layout, top to bottom:

1. **Contract comment.** One short block: what the module does, its inputs and outputs, and the failure it is responsible for. Plain sentences, no decoration.
2. **Limits block.** All named limits for the module together, as constants in `SCREAMING_SNAKE_CASE` with units in the name (`FETCH_TIMEOUT_MS`, `MAX_FEEDS`, `QUEUE_CAPACITY`).
3. **Types.** The stage types in pipeline order (`ParsedX` → `ValidX` → `Plan` → `Result`), each with a one-line doc comment.
4. **The pipeline.** The exported function: a short list of stage calls in order, nothing else.
5. **Stages.** One function per stage, in the same order as the pipeline, each opening with its precondition asserts and closing with its postcondition asserts.
6. **Edges.** I/O helpers last, clearly named for their effect (`readManifest`, `writeReport`).

House idioms that make the signature consistent:

- Stage functions are verbs that name the stage: `parse…`, `validate…`, `plan…`, `execute…`, `verify…`, `report…`.
- One `assert(condition, message)` helper per package; messages state the invariant as a fact ("dedupe never adds urls"), not an error ("bad urls").
- Errors are a small union of named outcomes per pipeline (`{ kind: "timeout" } | { kind: "not_found"; path: string }`), never strings or generic `Error` subclasses.
- Tests are named for the guarantee they prove ("planFetches never exceeds MAX_FEEDS"), and every limit has a test that hits it.
- The same layout applies in Zig and Rust: limits as `const`, stages as functions in order, `std.debug.assert` / `assert!` at both ends.

## Elm-grade reliability in TypeScript

Elm apps famously run for years without runtime exceptions. That comes from rules, not magic, and TypeScript can enforce most of them. Every TypeScript project uses this setup.

| What crashes programs | Elm's answer | Our rule |
| --- | --- | --- |
| `null` / `undefined` | No null; absence is `Maybe` | `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`; no `!` |
| Thrown exceptions | No throw; failure is `Result` | Expected failures return a typed union (`{ ok: true; value } \| { ok: false; error }`); `throw` is only for broken invariants, via `assert` |
| Unchecked outside data | Decoders at every boundary | zod parse at every edge (HTTP, files, env, storage, model output, postMessage); no `as` after parsing |
| A forgotten case | Exhaustive pattern matching | Discriminated unions; every `switch` is exhaustive and ends in `assertNever` |
| Effects anywhere | Pure functions; effects are data (`Cmd`) run by the runtime | Pure stages in the middle, effects at the edges; stateful UI uses the Elm Architecture |
| Escape hatches | None | No `any`, `!`, `@ts-ignore`, unchecked `as`, or floating promises, enforced by lint |

**The Elm Architecture** applies wherever state matters: units, dashboards, sandbox switcher, and Native SDK cores. `Model` is a plain readonly type and `Msg` is a discriminated union. A pure `update(model, msg)` returns the next model plus effects described as data, which an edge runner executes. The view only reads the model and dispatches messages. Native SDK's TypeScript core works exactly this way.

```ts
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

function assertNever(value: never): never {
	throw new Error(`unhandled case: ${JSON.stringify(value)}`);
}

type Msg =
	| { kind: "fetch_started"; url: string }
	| { kind: "fetch_done"; url: string; items: number }
	| { kind: "fetch_failed"; url: string; error: FetchFailure };

function update(model: Model, msg: Msg): Model {
	switch (msg.kind) {
		case "fetch_started": return { ...model, pending: [...model.pending, msg.url] };
		case "fetch_done": return { ...model, pending: model.pending.filter((u) => u !== msg.url) };
		case "fetch_failed": return { ...model, failures: [...model.failures, msg.error] };
		default: return assertNever(msg);
	}
}
```

**tsconfig.json**, on top of the project's own settings:

```json
{
	"compilerOptions": {
		"strict": true,
		"noUncheckedIndexedAccess": true,
		"exactOptionalPropertyTypes": true,
		"noImplicitOverride": true,
		"noFallthroughCasesInSwitch": true
	}
}
```

**biome.json**, checked against Biome 2.5.10: it catches a missing switch case, `any`, `!`, an unsafe `as`, and an un-awaited promise. Several of these rules are in Biome's nursery and use its type inference, so re-check them when upgrading Biome.

```json
{
	"linter": {
		"domains": { "types": "recommended" },
		"rules": {
			"suspicious": { "noExplicitAny": "error", "noTsIgnore": "error" },
			"style": { "noNonNullAssertion": "error", "useThrowOnlyError": "error" },
			"nursery": {
				"noUnsafeTypeAssertion": "error",
				"useExhaustiveSwitchCases": "error",
				"noFloatingPromises": "error",
				"noMisusedPromises": "error"
			}
		}
	}
}
```

Adopting this in an existing repo surfaces many errors at once. Turn on the tsconfig flags first, fix the code, then enable the lint rules package by package. Never weaken a rule to get green: fix the code, or isolate the boundary in a parse function.

## Data: instant by default

Interfaces feel instant because their data is already there. Treat fetching and caching as part of the design, with named limits like everything else:

- **Render from cache first.** Anything seen before renders immediately from the local cache and revalidates in the background. A spinner is allowed only for data never seen before, and it reveals after 150 ms.
- **Prefetch on intent.** Hover, keyboard focus, and an item scrolling near the viewport start the fetch. By the time the click lands, the data is local.
- **One owner per entity.** Use a normalized cache keyed by id, so an update anywhere shows everywhere. Writes are optimistic and roll back as a typed failure, never silently.
- **Server caching is declared, not accidental.** Every cached read names its tag and lifetime, and every write invalidates the tags it touches. In Next.js use `"use cache"` with `cacheTag`/`cacheLife` and `revalidateTag` on writes, where the version supports it.
- **Stream, don't wait.** Send the shell and cached parts first and stream the rest. Never let one slow query hold the whole page.
- **GPU views get GPU-shaped data.** Graph and timeline payloads arrive as typed arrays (positions, colors, ids) that upload straight into vgpu buffers, not as arrays of objects that need a conversion pass.
- **Bounded and evicting.** Every cache has a size limit in bytes or entries and an eviction rule. Durable local caches live in `bun:sqlite` on the server or CLI and in IndexedDB in the browser.
- **The tools.**
  - **Endpoints:** better-call, so request and response types come from the zod schemas on the server and are shared with the client. Call them with better-fetch, or with the better-call client.
  - **Client cache:** SWR for simple reads (stale-while-revalidate, `preload` for prefetch on intent; vswarm already uses it). TanStack Query when a view needs mutations with optimistic updates and rollback, `prefetchQuery`, query-key invalidation, or a persisted cache.
  - Pick one per app, and don't mix both in the same view.
- **Measured.** Each key interaction has a latency budget (for example, under 100 ms to useful pixels on a cached route) and a trace that shows whether it holds.

## Example (TypeScript on Bun)

```ts
/**
 * Feed ingest. Takes a batch of feed URLs, fetches each once, stores new
 * items, and reports what changed. Owns the failure where one slow or broken
 * feed would stall the whole batch.
 */

const MAX_FEEDS = 500;
const FETCH_TIMEOUT_MS = 10_000;

/** A request whose shape has been checked. */
type IngestRequest = { feeds: { url: string }[] };
/** Unique URLs to fetch, with the time budget for each. */
type FetchPlan = { urls: string[]; timeout_ms: number; started_at: number };
/** The ways one feed can fail without failing the batch. */
type FetchFailure =
	| { kind: "timeout"; url: string }
	| { kind: "http_status"; url: string; status: number }
	| { kind: "unparseable"; url: string };

export async function ingestFeeds(input: unknown): Promise<IngestReport> {
	const request = parseIngestRequest(input);
	const plan = planFetches(request);
	const fetched = await executeFetches(plan);
	const stored = storeItems(fetched);
	return reportIngest(plan, fetched, stored);
}

function planFetches(request: IngestRequest): FetchPlan {
	assert(request.feeds.length > 0, "plan needs at least one feed");
	assert(request.feeds.length <= MAX_FEEDS, `at most ${MAX_FEEDS} feeds per batch`);

	const unique = [...new Set(request.feeds.map((feed) => feed.url))];
	const plan: FetchPlan = {
		urls: unique,
		timeout_ms: FETCH_TIMEOUT_MS,
		started_at: Date.now(),
	};

	assert(plan.urls.length <= request.feeds.length, "dedupe never adds urls");
	return plan;
}
```

Each stage is a thick block with a typed input and output, limits are named constants, and assertions guard both ends.

## Review checklist

When reviewing a diff, report findings as a table (Where · Now · Change to · Why), most severe first:

- [ ] The flow is a visible pipeline of named stages with typed seams
- [ ] Preconditions and postconditions are asserted; no stage trusts unchecked input
- [ ] Every loop, retry, queue, buffer, and wait has a named limit, and hitting it is handled
- [ ] Expected failures are typed results; nothing is swallowed or silently defaulted
- [ ] No `as` casts after parsing, no `any`, no `|| fallback` recovery
- [ ] Names carry units; booleans read as facts
- [ ] Nesting ≤ 3, no hidden branches, no unbounded recursion
- [ ] Each dependency is justified; no speculative abstraction
- [ ] Failure paths were exercised by a test or a run, not only the happy path
- [ ] Comments explain why
